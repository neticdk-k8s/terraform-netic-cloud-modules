# OpenBao seal — OVHcloud KMS (OKMS)

Creates the Secret that OpenBao's `seal "ovhcloud"` block reads, so the server
auto-unseals against OVHcloud KMS instead of needing manual unseal keys at every
start.

Supports both auth modes: **token** and **mTLS**.

## Which mode to pick

**Token is the practical default**, and what the Netic openbao chart already
expects — `OVHCLOUDKMS_TOKEN` is wired into `extraSecretEnvironmentVars` out of
the box.

|  | Token (PAT) | mTLS (access certificate) |
|---|---|---|
| Lifetime | can be set to **never expire** | **365 days maximum**, hard OVH limit |
| Chart changes | none | volume + `volumeMount` + changed env vars |
| Stored where | same Secret, same Terraform state | same Secret, same Terraform state |
| Scope | as broad as the PAT's IAM policy | bound to the OKMS domain |

The blast radius is identical — both credentials end up in the same Kubernetes
Secret and in Terraform state. What differs is lifetime and scope.

mTLS is stronger in principle: the credential is bound to the OKMS domain and
cannot be replayed against the rest of the OVH API. But the 365-day cap means
auto-unseal **breaks on the first restart after expiry**, so it only pays off
with a working renewal process. It also needs a change to the Helm chart, which
may live in a GitOps repo you cannot write to.

With a token, scope the PAT narrowly to OKMS and the difference is marginal.

## mTLS

The certificate is *yours*. OVH only signs it; the private key is generated by
you and never transits OVH when you use a CSR.

```hcl
# 1. Your keypair — never leaves your machine
resource "tls_private_key" "okms" {
  algorithm = "RSA"
  rsa_bits  = 4096
}

resource "tls_cert_request" "okms" {
  private_key_pem = tls_private_key.okms.private_key_pem
  subject { common_name = "openbao-seal" }
}

# 2. OVH signs it
resource "ovh_okms_credential" "openbao" {
  okms_id       = data.ovh_okms_resource.this.id
  name          = "openbao-seal"
  identity_urns = ["urn:v1:eu:identity:account:xx-xxxxx"] # who may use it
  csr           = tls_cert_request.okms.cert_request_pem
  validity      = 365 # days; 365 is the maximum
}

# 3. Into the cluster
module "openbao_seal" {
  source     = ".../bootstrap/openbao/seal/ovh"
  kubeconfig = module.service_cluster.kubeconfig

  okms = {
    endpoint = data.ovh_okms_resource.this.rest_endpoint
    kms_id   = data.ovh_okms_resource.this.id
    key_id   = data.ovh_okms_service_key.bao_seal_key.id
  }

  auth = {
    client_cert_pem = ovh_okms_credential.openbao.certificate_pem
    client_key_pem  = tls_private_key.okms.private_key_pem
  }
}
```

Without a `csr`, OVH generates the keypair and returns `private_key_pem` — but
only once: *"cannot be retrieved later"*. A credential created in the OVH portal
therefore **cannot** be used here, because its private key is gone. Either way
the key ends up in Terraform state, so treat state as a secret.

### Required Helm values

`OVHCLOUDKMS_CLIENT_CERT` / `_CLIENT_KEY` take file **paths**, not inline
content, so the PEMs must be projected into the pod as files. Patch your
HelmRelease:

```yaml
server:
  extraEnvironmentVars:
    BAO_CACERT: /openbao/userconfig/openbao-server-tls/ca.crt
    # Literal paths — these are not secrets
    OVHCLOUDKMS_CLIENT_CERT: /openbao/userconfig/openbao-seal/cert.pem
    OVHCLOUDKMS_CLIENT_KEY: /openbao/userconfig/openbao-seal/key.pem

  extraSecretEnvironmentVars:
    - {envName: BAO_SEAL_TYPE,        secretName: openbao-seal, secretKey: BAO_SEAL_TYPE}
    - {envName: OVHCLOUDKMS_ENDPOINT, secretName: openbao-seal, secretKey: OVHCLOUDKMS_ENDPOINT}
    - {envName: OVHCLOUDKMS_ID,       secretName: openbao-seal, secretKey: OVHCLOUDKMS_ID}
    - {envName: OVHCLOUDKMS_KEY_ID,   secretName: openbao-seal, secretKey: OVHCLOUDKMS_KEY_ID}
    # OVHCLOUDKMS_TOKEN is removed in mTLS mode

  volumes:
    - name: openbao-seal
      secret:
        secretName: openbao-seal
        defaultMode: 0400
        items:
          - {key: client_cert.pem, path: cert.pem}
          - {key: client_key.pem,  path: key.pem}

  volumeMounts:
    - mountPath: /openbao/userconfig/openbao-seal
      name: openbao-seal
      readOnly: true
```

One Secret serves both roles: env vars for the coordinates, and a selectively
projected volume for the two PEM files.

## Token

```hcl
auth = { token = var.okms_token } # OVHcloud Personal Access Token
```

Needs no volume and no chart change: the chart's existing `OVHCLOUDKMS_TOKEN`
entry in `extraSecretEnvironmentVars` is enough.

A PAT belongs to a **local IAM user** and inherits that user's permissions, so it
needs an IAM policy — without one OKMS answers `403 Forbidden` even though the
token itself is valid. The crypto actions live on the `okms/serviceKey` resource
type, not `okms`:

```hcl
resource "ovh_iam_policy" "openbao_seal" {
  name       = "openbao-seal"
  identities = [data.ovh_me_identity_user.openbao.urn]
  resources = [
    data.ovh_okms_resource.this.iam.urn,              # the domain
    data.ovh_okms_service_key.seal_key.iam.urn,       # the key
  ]
  allow = [
    "okms:apikms:serviceKey/get",
    "okms:apikms:serviceKey/encrypt",
    "okms:apikms:serviceKey/decrypt",
    "okms:apikms:serviceKey/dataKey/create",
    "okms:apikms:serviceKey/dataKey/decrypt",
  ]
}
```

Note the `apikms` prefix — that is the KMS data plane the plugin talks to.
`apiovh` actions target the OVH control plane and are not what the seal uses.
Discover the exact names with
`data "ovh_iam_reference_actions" { type = "okms/serviceKey" }`.

Create the PAT in the OVH Manager under **Identity, Security & Operations →
Identities** → the user's `…` menu → **Manage tokens**. Disable the expiry toggle
for a non-expiring token.

## Inputs

| Name | Type | Default | Description |
|------|------|---------|-------------|
| `kubeconfig` | `string` (sensitive) | — | Raw kubeconfig for the cluster OpenBao runs in |
| `okms.endpoint` | `string` | — | OKMS REST endpoint |
| `okms.kms_id` | `string` | — | UUID of the OKMS **domain** |
| `okms.key_id` | `string` | — | UUID of the AES **service key** (encrypt + decrypt) |
| `auth.client_cert_pem` | `string` (sensitive) | `null` | mTLS certificate PEM |
| `auth.client_key_pem` | `string` (sensitive) | `null` | mTLS private key PEM |
| `auth.token` | `string` (sensitive) | `null` | OVHcloud PAT (token mode) |
| `namespace` | `string` | `"netic-vault-system"` | Namespace OpenBao runs in |
| `namespace_timeout_seconds` | `number` | `180` | How long to wait for GitOps to create the namespace before creating it |
| `create_namespace` | `bool` | `true` | Create the namespace if the wait expires — see below |
| `secret_name` | `string` | `"openbao-seal"` | Must match the chart's `secretName` |
| `statefulset_name` | `string` | `"openbao"` | StatefulSet to roll on change |
| `restart_statefulset` | `bool` | `true` | Roll the StatefulSet when seal values change |

On a freshly built cluster Terraform normally reaches this module before Flux has
reconciled the namespace, and a plain apply would fail with `NotFound`. The
module waits, then creates it.

Creating it is not just a workaround: the GitOps Kustomization that would create
the namespace also carries OpenBao's `Certificate`, which cannot be validated
until the namespace exists. Getting there first breaks that deadlock. Flux adopts
the namespace on its next reconcile. Set `create_namespace = false` to fail
instead, if namespace creation must stay with GitOps.

Set **exactly one** auth mode. `kms_id` and `key_id` are two different UUIDs —
the domain and the key inside it; using one for both is the usual mistake, and
is rejected at plan time.

## Outputs

| Name | Description |
|------|-------------|
| `secret_name` / `namespace` | Where the Secret was created |
| `auth_method` | `"mtls"` or `"token"` — tells you which Helm values you need |
| `client_cert_path` / `client_key_path` | Secret keys to project as files (mTLS) |

## Notes

- **Certificate rotation.** `validity` maxes out at 365 days, so the credential
  expires and auto-unseal breaks on the next restart after expiry. Plan renewal.
- **Credentials never touch disk or argv** — the manifest is piped to `kubectl`
  over stdin. Provisioner config is not persisted in state, but the PEMs reach
  state through the `tls_private_key` / `ovh_okms_credential` resources, so
  `terraform.tfstate` must be treated as sensitive.
- `kubectl` must be on `PATH` (same requirement as `bootstrap/gitops`).
